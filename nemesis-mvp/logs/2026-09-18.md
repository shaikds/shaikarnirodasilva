# Work log — 2026-09-18

## P11 closed — Jev plays the player (M9, developer-requested; TypeSafe System One)

- **Request:** add TypeSafe.ai's Jev as an option to play the fighter,
  designed so it genuinely "lives" in the game per this project's own
  rules — with an explicit design instruction to keep **state** (what
  Jev is told) and **questions** (what Jev is asked) strictly separate.
  Read the `typesafe-ai` skill before designing anything.
- **Read first:** the skill's docs-index and API links
  (`docs.typesafe.ai/...`) are **blocked by this build environment's
  network egress policy** — every fetch attempt (direct `curl`, `WebFetch`)
  returned `EGRESS_BLOCKED`. The skill's own fallback rule applies: "if
  live access is unavailable, use available local docs or installed SDK
  types, state that limitation, and avoid inventing version-dependent
  details." The `typesafe-ai/skills` GitHub repo was cloned to check for a
  vendored reference — it carries only the same pointer doc, nothing
  further. No npm package under a discoverable TypeSafe/Jev name was
  found either. **Consequence, stated plainly:** the exact HTTP wire
  format (field names, response envelope) in `ai/jev.js` /
  `tools/jev-proxy.mjs` is an assumption, not a verified contract. It is
  confined to ONE adapter (`JevBackend.send` + `_normalize`), defensively
  normalizes several plausible response shapes (an `answers` map, a
  `results` array, `answer`/`value`/`choice`/`label` field aliases,
  `probability`/`p`/`confidence` aliases), and is verified against a mock
  backend + a mocked `fetch`, not the live service. Everything the skill
  DOES describe in prose — the state/questions split, Choice/Noul
  primitives, one batched request of independent questions, instructions
  vs. criteria, speculative premises stated explicitly, typed answers with
  probabilities — is followed exactly; only the literal bytes on the wire
  are a placeholder pending the real docs.
- **Built (FR-9.1 — the state/questions split, followed to the letter):**
  - `ai/jev.js`: `buildFightState()` returns ONLY observed facts as named
    JSON fields — `me` (hp/energy/surge/flying/canFly/state/power), `foe`
    (name, level, hp, **state AND phase** — a wind-up, a stagger, and a
    charge are different worlds), `duel`, `recent` (last 4 combat events
    as short strings), `rivalry` (record, hate, last taunt heard, macro
    threat), `lastDirective` (+ outcome). No inferred conclusions live in
    state — inference is entirely the model's job.
  - A static 4-question bank, each with `instructions` (the judgment) and
    `criteria` (the possible answers, described as concrete situations):
    Choice `next_move` over an 11-option tactical vocabulary covering the
    whole M7/M8 kit (press_attack, route_uppercut, charge_blast,
    headbutt_rush, ki_pressure, special_beam, guard, evade, take_flight,
    close_distance, back_off); speculative Noul `commit_full_charge`
    (premise stated explicitly: "assume JEV begins charging THIS instant
    ... will the hold reach FULL charge and land unpunished?"); Noul
    `danger_now`; Choice `voice` — Jev SELECTS one of 8 canned lines or
    `stay_silent` (the no-match outcome), never generates text.
  - All four questions batch into ONE request per decision, run
    independently over the same state (verified: no question consumes
    another's answer).
- **Built (FR-9.2 — code owns the workflow):**
  - `ai/jevPlayer.js`: `JevPlayerDriver` executes directives through the
    exact Fighter API a human drives — `canStart`/`startAttack`/
    `startCharge`/`startDodge`/etc. Frame legality and timing stay
    deterministic code; Jev only supplies which move, how committed
    (charge hold length gated by `commit_full_charge`'s probability: >0.55
    → hold to full/BLAST, else an early safe release), how alert
    (`danger_now` arms a dodge reflex independent of the chosen move), and
    what to say.
  - Cadence: a fresh judgment on directive completion, ~1.4s staleness, or
    a salient event (foe staggered, a blast landed/taken, duel start). The
    CURRENT directive keeps executing while a request is in flight — a
    freshness sequence number discards a stale answer for a directive
    that already moved on.
  - Liveness (AC-9.2.3): any failure — no backend running, a timeout, a
    bad response — sets `offline` and falls back to a heuristic bot
    (reused from `PlayerBot('aggressive')`) so the duel never stalls; the
    HUD/panel shows `JEV · OFFLINE`; a retry probes every 5s.
  - Runtime toggle (`ui/jevPanel.js`, "LET JEV PLAY"): swaps the live
    player driver; the profiler/sync/zenkai systems are unmodified and
    cannot distinguish Jev's fighter from a human's.
- **Built (FR-9.3 — credentials never in the repo or bundle):**
  - `tools/jev-proxy.mjs`: a zero-dependency local Node proxy that holds
    `TYPESAFE_API_KEY` server-side and forwards to the (assumed) upstream
    endpoint — the page's default `url` points here
    (`http://localhost:8765/decide`). A direct browser-side key is also
    available in the panel, clearly marked dev-only, stored in
    `localStorage` only.
- **Bugs caught during testing (both real, both fixed before close):**
  1. `lastDirective` (the living-memory feedback field) was finalized
     inside `_apply()` — i.e., only once a NEW answer arrived — so it was
     always one decision late and the state sent with the very next
     request never actually carried the previous directive's outcome.
     Fixed: the outcome is now snapshotted at ASK-time (top of
     `_maybeAsk`, before `buildFightState`), without clearing the still-
     executing directive object, so cadence (AC-9.2.2) and memory
     (AC-9.1.1) both hold together.
  2. A test setting `player.energy = 60` (exactly `ENERGY.specialCost`)
     made the offline-fallback bot's random special-beam roll (35% chance
     at range) flakily eat the entire movement-check window with a
     0.48s windup. Not a driver bug — a non-deterministic test fixture.
     Fixed by zeroing energy before the fallback movement probe.
- **Verification:** `tests/p11_jev.spec.mjs` 34/34 — state shape (incl.
  "no inferred conclusions" check), the 4-question bank's exact shape,
  typed-answer consumption (move execution, charge-commit gating with
  real blast/no-blast outcomes, danger reflex independent of the chosen
  move, voice selection vs. silence), cadence + in-flight persistence +
  freshness, living memory (recent events + last-directive outcome + last
  taunt heard all feed the next request), offline liveness (HUD +
  fallback movement), runtime toggle, profiler blindness to who's
  driving, and the actual wire body via a mocked `fetch` (state/questions
  as separate top-level fields, model field present, Bearer header only
  when a key is configured). Full p0–p11 regression green; p8 fairness
  band ×2.

## P12 closed — Jev as the nemesis (M10, developer-requested follow-up to M9)

- **Request:** "i wanted jev to be the nemesis." M9 (above, same day) had
  built Jev as the PLAYER's controller, per the literal wording of the
  original request ("add TypeSafe.ai JEv model as the player"). The
  developer's actual intent was for Jev to drive the rival itself.
- **Decision:** keep M9's player-side driver — it's already shipped,
  tested, and zero-risk to leave in place — and ADD the nemesis-side
  driver as a genuinely separate, independently toggleable capability,
  rather than replacing one with the other. "Jev fights Jev" (both
  toggles on) is even a legitimate, slightly delightful option now.
- **Built:**
  - **Shared vocabulary, split framing (FR-10.1):** `ai/jev.js`'s
    question bank was extracted from a flat constant into
    `buildQuestions(persona)`, keeping `QUESTIONS = buildQuestions(PLAYER_PERSONA)`
    exported unchanged so every M9/p11 test kept passing untouched. A new
    `ai/jevNemesis.js` supplies a nemesis-framed persona ("You are JEV,
    the undying nemesis of the fighter described in `foe`...") and calls
    the SAME builder — one rulebook, two voices, zero duplicated
    criteria text. Its `buildNemesisState()` reads the fight from the
    rival's own point of view: `me` carries its in-world name/level/
    power (it knows who it is); `rivalry` carries its OWN hate
    (`myHate`, not `foeHate`), the win/loss record, and its three most
    recent ledger memories verbatim via `ledger.last(3)` — richer than
    the player-side state, because the nemesis is the one who has lived
    this rivalry and owns its memory.
  - **Executor that augments, not replaces (FR-10.2):**
    `ai/jevNemesisDriver.js` drives `rival` through the identical Fighter
    API `RivalAgent` and a human both already use. The gate for "a real
    duel is happening" is `RivalAgent.enabled` — the ONE existing
    flow/macro-owned source of truth for that — not a re-derived
    condition. On ANY failure (no backend, timeout, bad response) the
    fallback is `RivalAgent.update()` ITSELF, not a generic bot: this
    makes the S-3 fairness band hold by construction whenever Jev is
    offline, since offline behavior literally IS the already-tuned GOAP
    brain. Cadence, freshness, and in-flight persistence are the exact
    same contract as M9.
  - **Independent activation (FR-10.3):** `ui/jevPanel.js` was
    generalized from a hardcoded single `#jev` element into a reusable,
    positionable component (`id`, `bottom`, custom labels). Two
    instances now exist — "LET JEV PLAY" (unchanged position/behavior)
    and "JEV IS THE NEMESIS" (stacked above it). `JevBackend` gained a
    `storageKey` constructor param so each side's backend config
    (endpoint/model/key) persists under its own localStorage key —
    verified no cross-talk: configuring one side's key never touches the
    other's.
- **Real bug found in testing (not a design flaw — an interaction with
  an EXISTING documented GOAP rule):** `JevNemesisDriver` hands off to
  the fallback for any tick where its own directive is still null — by
  design, exactly like M9's player driver, so the fighter is never idle
  while waiting for the first answer. In a test that had cleared
  `RivalAgent.currentPlan`/`currentAction` to give it a "clean slate,"
  this meant GOAP's own "nothing to do → replan NOW, `replanT` is a
  staleness ceiling not a gate" rule (documented back at P3) fired
  unconditionally on that fallback tick and could commit the rival to an
  attack — which then blocked Jev's own directive from executing until
  that attack naturally finished. Fixed on the TEST side, not the
  driver: a wider tick budget so the transient GOAP action has room to
  complete, and `rivalAgent.plannedDefense = null` in setup — the exact
  isolation convention `p3_rival.spec.mjs` already established for this
  same agent.
- **Verification:** `tests/p12_jev_nemesis.spec.mjs` 21/21 — shared
  question vocabulary + nemesis-framed persona, rival's-own-eye state
  shape (name/level/power, own hate, record, ledger memories, no stored
  foe name), executor parity (dodge/charge/blast through the shared
  Fighter API), the `RivalAgent.enabled` gate, GOAP fallback proven via
  a mocked rejection (the unmocked-real-fetch variant was trimmed from
  the final suite — it proves the identical code path but trips every
  other suite's "no console errors" convention with a browser-level
  `ERR_CONNECTION_REFUSED` log), cadence/freshness parity with M9, voice
  through the canonical subtitle channel under the rival's own name, and
  independent toggling + config isolation (both/either/neither active).
  Full p0–p12 regression green; p8 fairness band ×2 (structurally
  guaranteed to hold, since the default and every offline path is pure
  GOAP, unchanged from P3–P10).
