## On-screen Jev error visibility (AC-9.2.3 extension)

- **Request:** the developer hit real friction getting Jev connected —
  couldn't reliably open browser dev tools (F-keys default to system
  media controls on macOS without Fn; right-click is intercepted by the
  game as the block button; a published artifact renders in an iframe
  so the top-level console doesn't show its logs) — and, reasonably,
  expected me to be able to run a live check against their machine.
  Corrected that misunderstanding plainly: this session has no path to
  a developer's own browser or `localhost` under any circumstance — it
  isn't a permission or tooling gap, `localhost` is a private address
  that only resolves on their own machine. Verified with a live test:
  attempting `curl` to `api.typesafe.ai` from this environment failed
  with a hard organization-policy 403 at the egress proxy — the same
  wall that blocked `docs.typesafe.ai` all along — proving this sandbox
  has no route to TypeSafe at all, let alone to someone else's laptop.
- **Real fix, not just an explanation:** since dev tools access itself
  was the actual blocker, removed the need for it. `JevBackend.send()`
  (`ai/jev.js`) now throws specific, human-readable errors instead of a
  bare `jev http ${status}`: a network/CORS failure names both
  possibilities plainly (`network error reaching <url> — proxy not
  running, wrong URL, or CORS blocked it (<native message>)`), a bad
  HTTP status includes the status code AND up to 200 chars of the
  response body (so a `401` shows the actual "invalid key" text), and a
  timeout is reported as a timeout, not folded into a generic error.
- Both drivers (`ai/jevPlayer.js`, `ai/jevNemesisDriver.js`) now capture
  this into `driver.lastError`, cleared on any successful exchange.
  `ui/jevPanel.js` grew a small red `.err` box under the toggle,
  user-selectable text, that shows the live error whenever the panel is
  active and offline — **directly on the game page, no dev tools
  required at all.**
