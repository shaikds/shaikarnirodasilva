## P13 closed — Mobile: touch controls & responsive layout (M11)

- **Request:** "if you detect the device is mobile, add on-screen
  buttons and responsiveness."
- **Built:**
  - `core/device.js`: one `isMobile()` — touch-capable (`ontouchstart`,
    `maxTouchPoints`, `pointer: coarse`) AND phone-sized
    (`min(innerWidth, innerHeight) < 760`). A touchscreen laptop with a
    normal-sized display deliberately stays on the desktop experience.
    Read once at boot, sets `body.mobile` for every module's CSS.
  - `core/input.js` grew two small public methods, `press(action)`/
    `release(action)`, that write the EXACT SAME `down`/`pressT` state a
    keydown/keyup already does, plus a `touchAxes` override that
    `moveAxes()` prefers over the WASD-derived vector when set. This is
    the whole trick: `PlayerController` needed ZERO changes — touch
    controls are just a second producer of the same Input state the
    rival's GOAP-vs-Jev drivers already modeled for combat.
  - `ui/touchControls.js`: a virtual joystick (bottom-left, continuous
    axes via drag distance/angle), a full-screen drag zone (camera
    orbit, feeding the same `mouseDX`/`mouseDY` pointer-lock mouselook
    already writes), and on-screen buttons for the full action set
    (light, heavy, block, dodge, special, ki, dash, flight, jump/rise,
    descend, lock-on) — each just calling `press()`/`release()` on
    touchstart/touchend. Heavy's hold-to-charge needed no special
    handling at all: the controller already gates charge start/release
    on `down.heavy`, so a touch hold IS a charge hold.
  - Responsive layout (`body.mobile` CSS across `ui/hud.js`,
    `ui/jevPanel.js`, `ui/keymap.js`, `index.html`): HP bars move to the
    top corners, both Jev panels move to the top-left stacked, the fps
    readout hides, the key map collapses to one column and shows
    touch-instruction rows (joystick/drag/buttons) instead of keyboard
    rows, with a small always-present `?` button replacing `H` (no
    keyboard to press it from). Page-level gestures that would fight a
    game (pinch-zoom, pull-to-refresh, double-tap-zoom) are suppressed
    on the game surface.
  - `ui/jevPanel.js` was generalized from fixed `bottom`/`top` params to
    an arbitrary `pos: {left,right,top,bottom}` object, so the mobile
    layout could move both panels clear of the touch-button cluster
    without a parallel positioning system.
- **Two real bugs caught by actually looking at a screenshot, not just
  green tests:**
  1. The playable artifact's build wrapper (a script in the working
     scratchpad, not part of the committed repo) never carried the
     `<meta name="viewport">` tag from `index.html` into the built page.
     Confirmed via direct measurement: a real mobile browser opening the
     artifact link without that tag falls back to Chromium's legacy
     ~980px virtual viewport — which is `>= 760`, so the game's own
     `isSmallScreen()` check would have silently failed and NO touch
     controls would have rendered for the exact real-world case (someone
     opening the link on their phone) that this whole feature exists
     for. The dev-server tests never caught this because they load
     `index.html` directly, which already has the tag — only testing the
     actual built artifact surfaced it. Fixed in the build script, and
     the artifact was rebuilt+verified under real mobile emulation
     (`innerWidth` now correctly reads 390, not 980) before redeploying.
  2. A screenshot of the in-game (not just the key-map overlay) mobile
     layout showed the TUTORIAL's own prompt text ("MOVE / W A S D") —
     `core/states.js` keeps its own device-specific strings, entirely
     separate from the key-map overlay, and hadn't been touched. Added a
     `TUTORIAL_STEPS_MOBILE` table and branched the one other
     key-naming prompt (the post-awakening "F fly · Space/C · hold Q ·
     I ki blast" message); `GameFlow` now takes `mobile` in its ctx.
- **Regression discipline:** this is purely additive and gated entirely
  on `isMobile()` — a desktop session gets no touch DOM, no `mobile`
  body class, `touchControls === null`, and an unchanged key map.
  Verified explicitly (not just assumed) in the same test run as the
  mobile checks.
