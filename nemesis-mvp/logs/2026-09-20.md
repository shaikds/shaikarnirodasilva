# Work log — 2026-09-20

## Root cause of "Jev offline" found and fixed — `questions` wire shape (AC-9.3.2 correction)

- **Evidence:** the developer sent a screenshot of a real `422
  Unprocessable Entity` returned by their own running `tools/jev-proxy.mjs`
  while forwarding a request to TypeSafe:
  ```
  {"detail":[{"type":"dict_type","loc":["body","questions"],
    "msg":"Input should be a valid dictionary", ...}]}
  ```
  This was only visible at all because of the on-screen error text built
  the night before (AC-9.2.3 extension, see 2026-09-19 log) — the
  developer has no reliable path to browser dev tools on their machine,
  and this environment has no network path to their `localhost` or to
  `api.typesafe.ai` (hard organization-policy 403 at the egress proxy,
  confirmed again today) to reproduce it directly. The fix was made from
  the developer's own error report, not from a live reproduction.
- **Root cause:** `JevBackend.send()` (`src/ai/jev.js`) was serializing
  `questions` as a JSON array of `{id, type, instructions, criteria}`
  objects. TypeSafe's real System One endpoint validates `questions` as a
  **dictionary keyed by question ID** (Pydantic `dict_type` rejection
  proves the array was never valid). The prior corroboration (convergent
  independent SDKs, 2026-09-18) got the state/questions separation, the
  endpoint, the auth, and the response shape right, but missed this one
  structural detail on the request side.
- **Fix:** added `JevBackend._toQuestionsDict()`, called only inside
  `send()` at the exact point the request body is built. Converts the
  internal array-of-`{id,...}` shape (kept everywhere else — code and
  tests — because it's more ergonomic to iterate and assert on) into
  `{id: {...}}` right at the wire boundary. No other call site, no test
  fixture outside the wire-contract check itself, and no internal
  representation changed.
- **Verification:**
  - `tests/p11_jev.spec.mjs`: the AC-9.3.2 wire-contract check now
    asserts `questions` is a plain object keyed by id (`Object.keys(...)
    .join(',') === 'x'`, no `id` field inside each entry) instead of the
    old, now-known-wrong array assertion. All checks pass.
  - `tests/p12_jev_nemesis.spec.mjs` (exercises the same `JevBackend`
    from the nemesis side): all checks pass, unchanged.
  - Full regression, `tests/p0_boot.spec.mjs` through
    `tests/p13_mobile.spec.mjs`: **all green in one pass**, including the
    two previously-flaky checks (`p8_acceptance`'s "the post-genesis duel
    resolves with full rivalry bookkeeping" and `p9_saiyan`'s
    aerial-pursuit-altitude check) — clean this run, consistent with
    their documented non-deterministic (unseeded RNG / timing) nature
    rather than anything reintroduced here.
  - p8's S-3 fairness band (20 duels, neither side over 70%) run twice,
    both green.
- **Scope discipline:** this was a one-line-of-reasoning fix confined
  entirely to the wire boundary in `src/ai/jev.js`. Nothing in
  `jevPlayer.js`, `jevNemesis.js`, `jevNemesisDriver.js`, `jevPanel.js`,

## Second follow-up 422 — Noul `criteria` must be an object, not a string

- **Evidence:** immediately after the fix above was pulled, the developer
  sent a second screenshot of a real `422` from the same proxy, this time
  narrower:
  ```
  {"detail":[{"type":"model_attributes_type",
    "loc":["body","questions","commit_full_charge","noul","criteria"],
    "msg":"Input should be a valid dictionary or object to extract
    fields from","input":"Yes me[ans...]"}]}
  ```
  (the `"noul"` segment in `loc` is Pydantic's discriminated-union
  reporting convention — it names which tagged variant was being
  validated, not a literal nested key in the request body the code
  needed to add.)
- **Root cause:** `buildQuestions()` (`src/ai/jev.js`) defined each Noul
  question's `criteria` as one plain instructional string ("Yes means
  ... No means ..."). TypeSafe's schema requires a Noul's `criteria` to
  be a **dictionary with `yes`/`no` keys**, the same way a Choice
  question's `criteria` is already correctly a dictionary keyed by
  option — Noul is a two-option Choice in this respect, not a special
  case. This was missed by the SDK corroboration because the examples
  those integrations exercised didn't happen to cover a Noul question.
- **Fix:** split each of the game's two Noul questions
  (`commit_full_charge`, `danger_now`) into `criteria: { yes: '...', no:
  '...' }`. No wire-boundary conversion needed this time — criteria is
  sent exactly as authored, so the fix lives at the question-bank
  source, shared automatically by both the player and nemesis drivers
  via `buildQuestions(persona)`.
- **Verification:** added a check to `tests/p11_jev.spec.mjs` asserting
  both Noul questions' `criteria` are `{yes, no}` objects — passes. Full
  regression (`p0`–`p13`, all green in one pass, including p12 and the
  two historically-flaky checks), p8 S-3 band run twice, both green.
  Committed, pushed, and the artifact rebuilt and redeployed to the same
  URL.
- **Status:** with both corrections in place, every structural detail of
  the request body that TypeSafe's own validator has surfaced so far is
  now correct. If a third issue surfaces it will most likely be on the
  RESPONSE side (an unrecognized field shape `_normalize` doesn't
  already handle) rather than the request — the on-screen error panel
  will show it exactly as before.
